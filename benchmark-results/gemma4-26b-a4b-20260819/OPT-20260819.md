# Gemma 4 26B-A4B local optimization (2026-08-19)

## Result

The production recommendation for the local GTX 1660 Ti is the native SM75
build, 21 fixed experts per layer, the balanced 12-prompt profile, Q8_0 KV,
decode batch 32, eight CPU threads, and no speculative decoder. The launcher is
`start-gemma4-26b-a4b.sh`.

The final three 256-token runs produced the same token hash and measured:

| run | prompt tok/s | decode tok/s |
| ---: | ---: | ---: |
| 1 | 38.884 | 34.611 |
| 2 | 38.935 | 34.647 |
| 3 | 38.923 | 34.667 |

Median decode throughput was 34.647 tok/s. Peak observed VRAM after the run was
5216 MiB. The benchmark used the System76 performance profile; the normal power
profile was restored after testing.

so S21 is the promoted upper limit for this 6-GiB card.

## Source synchronization

The original `miltos22/llama-wackMall` main branch had no commits newer than
the local branch. The merge-request repository contains a substantially
different expert-tier architecture and is not safe to merge wholesale into the
current adaptive/cache/lookahead branch. Three isolated compatibility and CUDA
fixes were ported instead:

- quantized CUDA copy launch geometry (`c7a392699065`)
- fused RMS-norm/mul/RoPE path (`a22fd30e471`)
- reshaped quantized tensor stride calculation from `dbc96d833401`

The focused CUDA copy and fused RoPE backend tests passed on both relevant
builds.

## MTP follow-up (2026-08-20)

A short adaptive screen compared MTP widths, target and draft KV types, decode
batch sizes, expert residency, and the MTP CPU row paths. Each screen used one
64-token warm-up followed by two deterministic 256-token runs.

| configuration | median decode tok/s | result |
| --- | ---: | --- |
| control, no MTP, Q8 KV, S21, decode 32 | 34.564 | stable control |
| MTP-2, Q4 KV, S15, decode 64 | 34.050 | stable but slower |
| MTP-2, Q4 KV, S15, decode 32 | 34.009 | no batch-32 gain |
| MTP-2, Q8 target KV, S15, decode 64 | invalid | repeat loop after 29 tokens |
| MTP-3, Q4 KV, S15, decode 64 | 31.173 | 48.2% acceptance |
| MTP-2, Q8-K/Q4-V draft KV | 33.080 | no reliable gain |
| MTP-2, Q4 KV, S17, decode 64 | 36.021 | short-screen winner |
| S17 plus CPU row reuse and multi-row | 34.454 | regression |
| MTP-2, Q4 KV, S18, decode 64 | invalid | repeat loop after 85 tokens |

The only stable MTP candidate was N=2, Q4_0 target and draft KV, S17, 768 MiB
VRAM reserve, decode batch 64, eight CPU threads, and CPU row reuse/multi-row
disabled. It used about 5148 MiB VRAM. S17 produced 56.3% acceptance in the
short screen; S18 changed the numerical path, reduced acceptance to 35.7%, and
entered a repeat loop.

The winner and the non-MTP production control were then compared with three
512-token runs on each of two long prompts:

| prompt | no-MTP median | MTP-S17 median | delta | MTP acceptance |
| --- | ---: | ---: | ---: | ---: |
| architecture | 33.560 | 32.364 | -3.6% | 52.5% |
| Go code review | 33.111 | 34.897 | +5.4% | 61.5% |
| combined six-run median | 33.335 | 33.880 | +1.6% | - |

Every final configuration generated all 512 requested tokens and had one stable
token hash across its three repetitions. MTP was not promoted: its combined
gain was below the 5% gate, prompt processing was slower, it required Q4 target
KV instead of the production Q8 KV, and the Q8 target path was unstable. The
S17 recipe remains a useful optional workload-specific MTP preset.
